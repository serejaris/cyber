# Secret Audit — аудит утечек секретов в репозиториях клиента

Авторизованная проверка кодовой базы клиента на утёкшие секреты: токены,
API-ключи, пароли, приватные ключи, сессионные файлы, закоммиченные БД.
Сканируется рабочее дерево, **вся git-история** (все ветки) и бинарные
артефакты (SQLite, Parquet, session-файлы). Главный агент — оркестратор:
зеркалирование, фанаут, верификация, отчёт. Сами сканы — в параллельных
субагентах-сканерах (по одному на репо, скелет промпта — в фазе 2).

## Порог входа

1. **Авторизация на аудит кода.** Клиент дал доступ (read-токен org,
   mirror-bundle, tarball, приглашение в org) — зафиксируйте доказательства
   доступа в материалах аудита, либо подпишите ROE с пунктом «secret
   scanning of source code». Публичный репо без явного доступа — вне этой
   дорожки (это задача пассивной разведки, не секрет-аудита).
2. **Аудит заведён в трекере:** ишью/тикер, привязанный к эгажменту
   клиента, рабочая ветка `check/<год>-<месяц>-<день>-<slug>`.
3. **Секреты не покидают workdir.** Полные значения — только внутри
   рабочей директории аудита на время прогона; в findings и в отчёт —
   только masked (first4…last4) + sha256-12. Workdir после сдачи —
   `shred -u` / удалить.

## Фаза 0 — приём и зеркалирование (главный агент)

1. Зафиксировать в scope: список репо (или вся org), глубина истории,
   что считается секретом (по умолчанию — паттерны движка), разрешена ли
   live-проверка токенов (по умолчанию НЕТ).
2. Зеркалировать каждый репо: `git clone --mirror <url> $WORK/<repo>.git`
   — mirror хранит все ветки и рефлоги. Tarball без `.git` — об этом
   явно пишем в отчёт (история не проверялась). Workdir — вне аудируемых
   репозиториев (например `~/work/secret-audit-<client>/`); большие
   объёмы — на отдельной мощной машине.
3. Инвентарь: имя, размер, число коммитов, языки — вводная для фанаута.
   Монорепо > 1 ГБ — резать на пути, сканер получает под-пути.

## Фаза 1 — прогрев движка

Единый движок — the bundled sweep script:
rg-core (fallback grep), режимы text/names/binary + `--git-history`,
выход JSONL, вывод **всегда редактированный** (masked + sha256-12), exit
0/1/2. Обязательный smoke-тест перед каждым аудитом (не раз в жизни):
канарейка-директория с фейковыми секретами (маскирование проверяется
grep-ом на отсутствие полных значений в выводе). Если на машине есть
`trufflehog` / `gitleaks` —
запускать вторым слоем (они знают верификацию декодированных секретов и
провайдеров), находки мержатся по sha.

## Фаза 2 — фанаут сканеров (параллельные субагенты)

Одним сообщением, по одному агенту на репо (до ~10 параллельно). Скелет
промпта — копировать целиком и заполнить угловые скобки:

```
Ты — сканер секретов в репозитории <repo> аудита клиента <client>.
Workdir: <abs path к рабочей копии>. Читать можно всё, менять ничего нельзя.
1. Прогони движок: bash <sweep-script> \
     --root <worktree> --mode all --git-history > <workdir>/<repo>.jsonl
   (<sweep-script> — путь к the bundled sweep script; скопируй локально,
   если работаешь не с audit-хоста)
2. [если установлен] trufflehog git file://<worktree> --json > <repo>.th.json
3. Разверни mirror в worktree, если ещё не развёрнут (git clone <mirror> <wt>).
4. Прочитай выход. Для каждой находки: kind, путь, line/commit, masked, sha.
Отбей ложные: тестовые маркеры (EXAMPLE, test, dummy, your-, xxx, FIXME),
документация/фикстуры, библиотечные примеры — не находка, а note.
5. Сложи итог в <workdir>/<repo>.md: таблица находок (kind/prio/path/line
   или commit/masked/sha/статус real|test|doc) + счётчики + список
   «проверено, чисто». Полные значения секретов в отчёт НЕ писать.
Верни: счётчики по prio, топ-5 самых опасных (masked), путь к .md.
```

Если в вашем агентском фреймворке есть выделенные субагенты-сканеры,
вшейте этот скелет в их системный промпт — тогда в dispatch достаточно
workdir, репо и клиента.

## Фаза 3 — верификация (главный агент или отдельный верификатор-субагент)

1. **Дедуп** по sha256-12: один секрет в N файлах/репо = одна находка
   с перечнем мест.
2. **Классификация:** real (формат валиден, контекст прод), test
   (маркеры тестовых значений), doc (документация), expired-suspect.
   Апгрейд статуса — только новым доказательством.
3. **Глубина утечки:** первый коммит с секретом (`git log --all --oneline
   -S"<masked-prefix>"` по подстроке префикса в workdir), сколько коммитов
   носило, жива ли ветка. Публичный ли репо/форки — если известно.
4. **Live-проверка токенов — по умолчанию НЕТ.** Это активное действие
   против стороннего провайдера; только если ROE клиента прямо разрешает
   и только с изолированной audit-машины, по одному безвредному запросу
   на провайдера (getMe / whoami), ответ фиксируется как evidence.
5. У каждой находки фиксируется статус
   `candidate → validated / disproven / inconclusive`.

## Фаза 4 — отчёт (EN, клиенту)

Секции: Executive summary (counts),
Findings (по severity), Rotation checklist, Prevention. Severity:
P0 валидный прод-секрет · P1 тестовый/вероятный кред, сессии, БД с
токенами · P2 generic-кандидаты после триажа · P3 prevention-зазоры
(нет pre-commit, нет secret-scanning). Findings-файл —
`<date>-secret-audit.md` в папке findings аудита, всё masked.

**Rotation checklist** (обязательное приложение): какой секрет → у какого
провайдера ротировать → порядок (ротация раньше purge истории!), затем
`git filter-repo`/BFG + force-push + инвалидация форков/кэшей, затем
pre-commit hooks + secret scanning в CI + `--git-history` рескан.

## Гигиена

- Найти ≠ показать: клиенту — masked; полные значения не пересылаются
  даже в DM, клиент ротирует по своим каналам.
- Движок и субагенты не ходят в сеть (кроме live-проверки из фазы 3.4).
- Ресурс: на репо > 500 МБ истории — предупреждать о времени, `--max-mb`
  прикручивать осознанно (по умолчанию 10 МБ на файл в text-режиме).
