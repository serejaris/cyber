# Compromise Check (только чтение, по своим и авторизованным хостам)

## Вопрос, на который отвечает скилл

Входил ли кто-то, кроме владельца: **вошли или нет**. Не «какие слабые
места» (это `host-pentest`), не «есть ли конкретная дыра» (это
`php2shell-emergency`), а именно следы состоявшегося вторжения:
чужие входы, чужая настойчивость, чужие файлы, чужие соединения.

## Авторизация (жёсткий гейт)

- **Свой хост** (ваша рабочая машина, ваши VPS): спрашивающий и есть
  владелец; в отчёте пишем «owner-operated host».
- **Чужой хост**: письменное разрешение владельца до первого действия
  (сохранённая переписка или подписанный документ — доказательство
  авторизации). Без него ничего не делаем, даже по чтению через
  имеющийся доступ.
- Проверка **только читает**. Никаких удалений, киков сессий, правок
  ключей «по ходу»: находка фиксируется, решение за владельцем.

## Матрица проверок

Все команды читающие, время в UTC. Рассчитано на стандартный
Debian/Ubuntu-стек с systemd-journald.

### 1. Чужие входы

```bash
# успешные SSH-входы за окно, исключая известные адреса владельца и LAN
journalctl -q _COMM=sshd _COMM=sshd-session --since "<дата окна>" \
  | grep "Accepted" | grep -vE "<свои-IP-и-подсети>"
# пусто = чужих входов нет. Строки с [preauth] — это ОТКАЗЫ, не входы:
# их наличие норма (боты), важно что после них нет Accepted
```

### 2. Чужие ключи и учётки

```bash
ls -la /root/.ssh/                          # mtime authorized_keys vs окно
cat /root/.ssh/authorized_keys              # сверить каждый ключ со списком владельца
awk -F: '$3>=1000 {print}' /etc/passwd      # неожиданные UID
stat -c "%y" /etc/passwd                    # mtime старее окна = учётки не трогали
```

### 3. Настойчивость (persistence)

```bash
# новые systemd-юниты за окно; каждый новый сверить с хозяйскими
find /etc/systemd/system -type f -o -type l | xargs ls -la | awk '<окно дат>'
ls /etc/cron.d/ /var/spool/cron/crontabs/   # и сверить содержимое со стандартом дистрибутива
cat /etc/rc.local
grep "Install:" /var/log/apt/history.log    # неожиданные установки пакетов
```

### 4. Сеть: кто слушает и кто наружу

```bash
ss -tlnp | awk '$4 !~ /127\.|::1/'          # слушатели вне loopback, сверить со штатом
ss -tn state established                     # исходящие, исключив свои подсети
```

### 5. Файловые следы

```bash
find /tmp /dev/shm -type f -executable       # исполняемые во временных = красный флаг
```

### 6. Экспонированный веб-контейнер (если был открыт наружу)

```bash
# новые/изменённые PHP после маркера состояния
find /var/www/<сайт> -name '*.php' -newer <маркер>
# PHP в uploads = типичное место веб-шелла
find /var/www/<сайт>/wp-content/uploads -name '*.php'
# трофеи, за которыми приходят мародёры: дампы, .env, бэкапы
find /var/www -maxdepth 3 \( -name '*.sql' -o -name '.env*' -o -name '*.bak' \)
# учётки приложения: чужой админ — прямое подтверждение
wp user list --fields=ID,user_login,roles
```

### 7. Egress-глушитель как детектор (если стоит)

Если на хосте стоит блок исходящего трафика, пишущий дропы в журнал
ядра со своим текстовым маркером (префиксом правила): SYN-пакеты в
журнале = что-то внутри пыталось выйти в интернет. Ноль SYN =
активности наружу не было даже под обстрелом.

```bash
journalctl -k --since "<дата окна>" | grep '<маркер-egress-правила>' | grep -c ' SYN '
```

### 8. Медленный перебор

Логины по `wp-login`/`xmlrpc`, размазанные по часам: каждая минута
ниже порога штурма, поэтому считать попытки надо в окне часов, не
минут — реальный шторм выглядит как сотни POST за пару часов с одного
адреса.

```bash
# попытки входа одним адресом за окно, топ источников по убыванию
grep -hE 'POST /(wp-login\.php|xmlrpc\.php)' <access.log> \
  | awk '{print $1}' | sort | uniq -c | sort -rn
```

## Интерпретация

| Находка | Что это |
|---|---|
| Много `[preauth]` отказов | фоновые боты; норма, входа не было. Регулярный почасовой отказ одним алгоритмом — чья-то своя машина со старым ключом, спросить владельца |
| Новый ключ/юзер/юнит с mtime в окне | красный флаг; каждый новый юнит сверять со списком заведомо хозяйских (свои юниты изоляции/обслуживания известны заранее) |
| `Accepted` с неизвестного IP | подтверждение входа: дальше время, источник, что делал (journalctl по сессии), смена ключей по решению владельца |
| Исполняемый файл в /tmp, PHP в uploads | вероятный шелл: копия файла в доказательства, не удалять до разбора |
| Ровный поток POST на wp-login/xmlrpc от одного адреса, растянутый на часы | медленный перебор (блок 8); вход был только если в блоке 1 появился Accepted |
| SYN в egress-логе | что-то жило и рвалось наружу; искать по времени в журналах приложения |

## Вердикт и отчёт

Вердикт один из трёх: **чисто** (все блоки пусты/штатны),
**подозрительно** (несводимая находка без подтверждения входа),
**подтверждено** (Accepted с чужого адреса или живой шелл). Отчёт —
таблицей по блокам матрицы с вердиктом и временем; подозрительное
получает план следующего шага, подтверждённое — немедленная эскалация
владельцу. Готовый отчёт сохраняется в вашем стандартном месте
отчётов по инцидентам в этом же формате.

## Границы

- Читает журналы и ФС: не видит память процесса и то, что атакующий
  подчистил. Чистый вердикт = «следов не найдено», а не «взлома не
  было».
- Не заменяет форензику: при подтверждённом взломе — образ диска и
  разбор отдельной задачей.
